Thesis goal: Design and implement a production-grade, horizontally scalable image processing platform that demonstrates distributed systems patterns — async messaging, transactional outbox, and cloud-native orchestration.

The platform is built incrementally across 5 chapters, each introducing a new architectural layer — from a bare REST API through workers, frontend, and Kubernetes.

Problem & Motivation

The Challenge

  • Modern SaaS applications process thousands of images per minute — resize, watermark, format conversion
  • Synchronous processing blocks the HTTP connection for seconds, degrading user experience
  • A monolithic architecture cannot scale image processing independently from the API
  • A single server crash can silently lose queued work with no recovery mechanism

Requirements

  • REST API for file upload, metadata retrieval, and result download
  • Asynchronous processing — client gets an immediate 202 Accepted
  • Reliability — no job can be lost even if a service crashes mid-flight
  • Horizontal scaling — add more workers under load, remove them when idle
  • Security — reject malicious uploads before they reach the processing stage
The core problem: how do you decouple the "accept work" path from the "do work" path, guarantee delivery, and still scale each independently — without over-engineering a small team project?

Architecture Overview

API Service (Go)

Accepts uploads, validates files, stores originals in S3, records metadata in PostgreSQL. Exposes presigned download URLs.

Job Service (Go)

Creates processing jobs and reliably enqueues them to RabbitMQ using the transactional outbox pattern.

Workers (Python)

Consume one message at a time, process the image with Pillow, upload the result to S3, and update the job status directly in PostgreSQL.

Each service is independently deployable and scales separately — the core promise of microservices.

Microservice: API Service

Responsibility

The API Service is the single entry point for file ingestion. It accepts raw image uploads over HTTP, validates them, persists the file to object storage, and records metadata in PostgreSQL. It also serves presigned download URLs for both originals and processed results.

Endpoints

POST /api/v1/imagesUpload a new image
GET /api/v1/imagesList all images
GET /api/v1/images/:idImage metadata + download URL
Language: Go 1.22  ·  Port: :8080  ·  Module: image-platform/api-service

Upload pipeline (per request)

  • Parse multipart/form-data — stream file to memory
  • Read image header with image.DecodeConfig — no pixel decode
  • Reject if file size > MAX_UPLOAD_SIZE_MB or pixels > MAX_MEGAPIXELS
  • Generate UUID object key, stream file to S3
  • Insert row into images table in PostgreSQL
  • Return 201 Created with image metadata JSON

External dependencies

PostgreSQLimages table — metadata
S3 / MinIObinary file storage
The API Service is stateless — it holds no in-memory state between requests. Any replica can handle any request, which makes horizontal scaling trivial.

Microservice: Job Service

Responsibility

The Job Service manages the lifecycle of processing jobs. It receives a request to process an image, creates a job record in PostgreSQL, and reliably enqueues the job to RabbitMQ using the transactional outbox pattern. It also exposes an endpoint to query job status.

Endpoints

POST /api/v1/jobsCreate a processing job → 202
GET /api/v1/jobs/:idGet job status + result URL
GET /api/v1/jobsList jobs (filterable by status)
Language: Go 1.22  ·  Port: :8081  ·  Module: image-platform/job-service

Job creation — transactional outbox

  • Begin PostgreSQL transaction
  • Insert row into jobs table (status = PENDING)
  • Insert row into outbox_events table (published = false)
  • Commit — both rows saved atomically
  • Return 202 Accepted immediately
  • Background goroutine polls outbox → publishes to RabbitMQ

External dependencies

PostgreSQLjobs + outbox_events
RabbitMQpublish via outbox poller
The outbox goroutine runs every 500 ms (configurable via OUTBOX_POLL_MS). It batches unpublished events, publishes each to RabbitMQ, and marks them published = true.

Microservice: Processing Worker

Responsibility

The Processing Worker is a stateless consumer that picks up one job at a time from the RabbitMQ queue, downloads the source image from S3, applies the requested transformation using Pillow, uploads the result back to S3, and updates the job record in PostgreSQL — without any HTTP calls to other services.

Supported operations

resizeScale to given width × height
convertChange format (JPEG → PNG etc.)
watermarkOverlay text or image
thumbnailFast square crop + resize
Language: Python 3.12  ·  Library: Pillow  ·  Queue client: pika (AMQP)

Processing loop (per message)

  • Consume 1 message from RabbitMQ (prefetch_count=1)
  • Parse job payload — get job_id, operation, parameters
  • Set job status → PROCESSING in PostgreSQL
  • Download source image from S3
  • Apply Pillow transformation (resize / convert / watermark)
  • Upload result to S3 with a new object key
  • Set job status → COMPLETED + store result key in PostgreSQL
  • Acknowledge message to RabbitMQ

External dependencies

RabbitMQconsume jobs (AMQP)
S3 / MinIOdownload source, upload result
PostgreSQLupdate job status directly
If processing fails, the worker sets status → FAILED with an error message and nacks the RabbitMQ message (optionally requeuing it). The attempt_count field tracks retries.

Why Go for services? Go compiles to a single binary, has excellent concurrency primitives (goroutines) for the outbox poller, and produces small Docker images. Both services start in under 100ms.
Why Python for workers? The Python imaging ecosystem (Pillow) is mature and well-documented. Workers are stateless and CPU-bound — easy to scale horizontally regardless of language runtime.

Technology: MinIO — Object Storage

What is MinIO?

MinIO is an open-source, S3-compatible object storage server. It stores files as objects (blobs) identified by a bucket and an object key (a string path). Unlike a relational database, it has no schema — it stores any file type at any size.

In this project, MinIO runs as a Docker container in local development. In production on Kubernetes it is replaced by any S3-compatible cloud service (AWS S3, Google Cloud Storage, etc.) — the Go code does not change because the API is identical.

Why not store files in PostgreSQL?

  • Binary files in a database bloat WAL logs and make backups slow
  • S3 scales independently from the database — no IOPS contention
  • Object storage is designed for large, immutable blobs — it's much cheaper per GB
  • Presigned URLs let clients download directly from storage, bypassing the API server entirely

How it is used here

API ServiceUploads originals on POST /images
API ServiceGenerates presigned GET URL (TTL 60 min)
WorkerDownloads source, uploads result
ClientDownloads result directly via presigned URL

Presigned URL: a time-limited, cryptographically signed URL that grants read access to a single object without any credentials. The client downloads the file directly from S3 — the API server is not in the data path.

The Go client library is minio-go. Because MinIO speaks the same S3 API, switching to AWS S3 in production is a one-line config change — no code rewrite.

Technology: RabbitMQ — Message Queue

What is RabbitMQ?

RabbitMQ is a message broker — a server that accepts messages from producers and delivers them to consumers via named queues. It implements the AMQP 0-9-1 protocol.

A producer (Job Service) publishes a message to an exchange. The exchange routes it to a queue. A consumer (Worker) pulls from that queue, processes the message, and sends an acknowledgement (ack) when done. Only then does RabbitMQ delete the message.

Why RabbitMQ instead of direct HTTP?

  • Decoupling: Job Service does not need to know how many workers exist or where they are
  • Reliability: messages persist in the queue even if all workers are down
  • Load leveling: workers consume at their own pace — no API timeout, no back-pressure on the HTTP layer
  • Scaling: add workers without changing any configuration in Job Service

prefetch_count = 1

This setting tells RabbitMQ to send at most 1 unacknowledged message to each worker at a time. A new message is only dispatched after the previous one is acked.

  • Without it: RabbitMQ would push all queued messages to the first available worker, starving others
  • With it: a slow worker (large image) does not block faster ones — work distributes fairly
What happens if a worker crashes mid-job? Because the message was not acked, RabbitMQ automatically requeues it and delivers it to another worker — no job is lost.
RabbitMQ also has a Management UI (port 15672) that shows live queue depth, message rates, and consumer counts — useful for monitoring during load tests.

Pattern: Transactional Outbox

The problem it solves

A naive implementation of "create job + publish to queue" would do two separate operations:

  1. INSERT job into PostgreSQL
  2. Publish message to RabbitMQ

If the service crashes between steps 1 and 2, the job exists in the database but RabbitMQ never received the message — the job is permanently stuck with no worker ever picking it up.

The solution

Write the message to a database table (outbox_events) in the same transaction as the job. A separate background goroutine (the poller) reads unpublished rows and forwards them to RabbitMQ.

  • If the service crashes before publishing — the row is still in the DB, poller will retry
  • If the service crashes after publishing but before marking as published — the message is re-sent (at-least-once), worker must be idempotent
Key insight: by using the database as a reliable intermediate store, we reduce a distributed two-phase commit problem to a simple local transaction. The poller handles the async delivery with automatic retry — no external coordinator needed.

Technology: SPA — Single Page Application

What is an SPA?

A Single Page Application is a web frontend that loads once (a single HTML file) and then dynamically updates the content using JavaScript — without full page reloads. Navigation between "pages" is handled client-side by manipulating the DOM.

In this project, the frontend is a plain HTML/CSS/JavaScript SPA — no framework required. It communicates with the backend exclusively through REST API calls using the browser's native fetch() API.

Why SPA over server-rendered HTML?

  • The backend is already an API — no templating layer needed
  • A single static HTML file can be served from any CDN or Nginx container
  • Faster perceived performance — only data (JSON) is fetched after first load, not full HTML pages
  • Clean separation: backend owns data, frontend owns presentation

Frontend responsibilities

  • Upload form — drag and drop image, send multipart/form-data
  • Display upload progress and returned image metadata
  • Job creation form — select operation and parameters
  • Poll GET /api/v1/jobs/:id every few seconds to show live status
  • Display the processed result image when the job completes

Single base URL via Ingress

Because Kubernetes Ingress routes both /api/v1/images and /api/v1/jobs from a single hostname, the frontend only needs one configured base URL — it never knows or cares that two separate services exist behind it.

Chapter 4 of the thesis. Currently the backend is fully functional — the SPA is the remaining user-facing layer.

Technology: HPA — Horizontal Pod Autoscaler

What is HPA?

Horizontal Pod Autoscaler is a Kubernetes controller that automatically adjusts the number of running Pods in a Deployment based on observed metrics — typically CPU or memory utilisation.

When CPU usage exceeds the configured threshold, Kubernetes adds more replicas. When usage drops, it removes them. The process is fully automatic — no human intervention needed.

Horizontal vs Vertical scaling

  • Horizontal (HPA): add more identical pods — load is distributed. Preferred for stateless services.
  • Vertical: give each pod more CPU/RAM. Has limits, requires restart, harder to automate.

Workers are stateless — each one processes one job independently. Adding 10 workers = 10× throughput. This is the ideal case for horizontal scaling.

HPA configuration in this project

api-servicemin 1 · max 5 · CPU target 70%
job-servicemin 1 · max 3 · CPU target 70%
workersmin 1 · max 10 · CPU target 80%

Why 1–10 workers? Image processing (decode → transform → encode) is CPU-intensive. Under a burst of upload requests, worker CPU saturates quickly. A wide autoscaling range lets the platform absorb traffic spikes without pre-provisioning expensive hardware at all times.

Chapter 5 of the thesis includes load tests that demonstrate HPA kicking in — measuring throughput with 1 worker vs 10 workers under identical request rates.

End-to-End Data Flow

Steps 1–2: Synchronous path

The API Service validates the file header (without fully decoding it), rejects pixel bombs, and persists the original to S3 and metadata to PostgreSQL — all within a single HTTP request cycle.

Step 3: Hand-off

The Job Service creates a job record and an outbox event in a single database transaction. It immediately returns 202 Accepted with the job ID — the client is never blocked waiting for processing to complete.

Steps 4–5: Async path

A background goroutine polls unpublished outbox events and pushes them to RabbitMQ. Workers consume one message at a time, process the image, and write the result directly to S3 and PostgreSQL.

Key Architectural Decisions

Transactional Outbox

The job row and the outbox_event row are inserted in a single database transaction. A separate goroutine polls unpublished events and forwards them to RabbitMQ.

Guarantees at-least-once delivery even if the service crashes after writing to the DB but before publishing to the queue.

Worker → DB Direct

Workers update job status directly in PostgreSQL, without any HTTP call back to Job Service. This removes a synchronous dependency between services.

Job Service does not become a bottleneck or single point of failure for the processing pipeline.

prefetch_count = 1

Each worker fetches exactly one message from the queue at a time. RabbitMQ only dispatches the next message after acknowledgement.

Ensures fair load distribution across replicas — a slow worker does not starve faster ones.

Pixel Bomb Protection

image.DecodeConfig reads only the file header, never decoding pixels into memory. The megapixel check rejects the file before it is stored anywhere.

Prevents memory-exhaustion DoS attacks via crafted images (e.g. a 1 × 100 000 000 px PNG).

Presigned URL TTL

Processed results are served directly from S3 via a time-limited presigned URL (default 60 min). The API never streams binary file data to the client.

Eliminates a bandwidth bottleneck at the API layer and offloads large file transfers entirely to the object store.

Single Ingress

A Kubernetes Ingress routes /images to API Service and /jobs to Job Service. The client uses one base URL — services scale independently behind it.

Decouples client configuration from the internal service topology entirely.

Summary

What was built

  • Two production-grade Go microservices with full REST APIs
  • Reliable async messaging via the transactional outbox pattern
  • S3-based object storage with presigned URL delivery
  • PostgreSQL schema with outbox, partial indexes, and auto-trigger
  • Docker Compose local environment with health checks
  • Kubernetes manifests with HPA for all services

Patterns demonstrated

  • Transactional Outbox — reliable event delivery
  • At-least-once delivery with idempotent workers
  • Loose coupling — workers never call services over HTTP
  • Security-first file ingestion — pixel bomb protection

The platform demonstrates that a small team can build a reliable, scalable distributed system by applying well-known patterns (outbox, prefetch, presigned URLs) rather than complex custom infrastructure.
